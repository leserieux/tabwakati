## 2026-11-23 : phase 2, sécurité et rôles

- **Accès par page** : `core/auth/page-access.ts` (matrice page × permission, préfixe le plus long, refus par défaut, chemins ambigus refusés). Appliquée par le middleware à `/dashboard/*` **et à `/api/*`** (avant, les routes API ne dépendaient que de leur propre garde). Nouvelles permissions `exports.run` (finance, risque) et `settings.manage` (super-admin). Menu, onglets et accueil filtrés par rôle ; page `/dashboard/forbidden`.
- **Sessions révocables** : table `admin_sessions`, identifiant de session dans le jeton, vérification Edge avec cache de 30 s, révocation à la déconnexion, à la désactivation ou au changement de mot de passe d'un compte, et par « Déconnecter partout ». La connexion échoue (503) plutôt que d'émettre un jeton irrévocable si la session ne peut pas être enregistrée. Les anciens jetons (sans identifiant) restent valides jusqu'à leur expiration (12 h max).
- **Connexion** : 10 échecs en 15 minutes depuis une même IP bloquent les tentatives suivantes (429), en plus du verrouillage par compte.
- **Restriction par IP** (option `ADMIN_IP_ALLOWLIST`) : applique la liste à la console, à `/login` et à l'API ; `/api/cron/*` y échappe (protégée par `CRON_SECRET`).
- **Journal d'audit** : chaînage SHA-256 (migration `20261123095557`), historique repris sans modifier son contenu, `fn_admin_audit_verify()`, contrôle horaire avec alerte critique en cas de rupture.
- **Tests** : 62 → 109.
- **Double validation** (`src/core/approvals/`, migration `20261123212649`) : six actions sensibles exigent un **motif** (tracé dans le journal d'audit) ; avec `ADMIN_DUAL_CONTROL=on`, elles sont d'abord **demandées** puis **validées par un second super-admin nominatif** (page Système › Validations, expiration 24 h). La base garantit que le validateur est un autre compte nominatif actif (`fn_admin_decide_approval`), qu'une demande validée n'est exécutée qu'une fois (`fn_admin_claim_approval`) et qu'elle est rejouée avec les valeurs enregistrées, jamais celles d'un navigateur (contexte serveur privé). L'accès partagé historique ne compte jamais comme une personne.
- **Reporté volontairement** : 2FA et retraits (file de validation, retrait manuel). **Hors périmètre de la double validation pour l'instant** : fermeture d'une seule position, frais des actifs / Campay / prêts (page Réglages), collecte de trésorerie.

## 2026-11-22 : refonte structurelle (v0.3.0)

- **Structure** : code dans `src/`, rangé par domaine (`core/`, `modules/treasury|operations|users|revenue|products|wakati|system|metrics`). L'app mobile Flutter (qui partageait le dossier `lib/`) vit désormais dans `mobile/`. Les URL du dashboard ne changent pas.
- **Layouts** : 24 fichiers `layout.tsx` identiques supprimés ; les onglets de section sont rendus une seule fois par `app/dashboard/layout.tsx`. Effet de bord utile : « Réserve de retrait » et « Administrateurs » affichent enfin leurs onglets.
- **Sécurité** : le middleware vérifie maintenant la **signature et l'expiration** du jeton (Web Crypto, `core/auth/edge.ts`), plus seulement la présence du cookie ; garde commune des routes API (`core/auth/guards.ts`) ; la collecte réelle refusait à tort les comptes `super_admin` (corrigé) ; cookie `secure` seulement en production.
- **Performance** : un seul client Supabase par processus (avant : un par appel) ; navigation sans rechargement complet (`next/link`).
- **Crédit** : lecture des données et calculs extraits dans `modules/products/credit.ts` (testés) ; la page passe de 723 à ~520 lignes.
- **Hygiène** : `.env.example` sans valeurs réelles, `.gitignore` complété, `tsconfig.tsbuildinfo` retiré, dossier `docs/en_attente/` supprimé (copie identique de `modules/metrics/financial.ts`), README réécrit avec la roadmap.
- **Tests** : 41 → 62 (jeton Edge, navigation, rôles, crédit).
